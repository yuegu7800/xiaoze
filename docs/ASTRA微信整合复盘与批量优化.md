# ASTRA微信整合复盘与批量优化

2026-11-13。用户要求：复盘并优化已有整合，使用昨天构建的小泽自动接力；先把一批工作整好，最后统一测试。不是重新开发机器人，不把每轮用户试聊作为下一轮开发前置。

## 当前判断

完整微信入口已接入共用人物核心；原群/私/双会话、参与策略、旧配置、历史和关系工具没有删除。318项是上轮已执行的历史回归结果，不能替本轮修改背书。本次复盘为静态源码检查，尚未执行新的验证。没有真实语言样本，所以暂不能把表达自然度判为已改善，也不因缺真实样本就停掉已有具体实现任务。

发现的优先缺口与核查依据：

1. **群多人上下文与回复对象。** `IntegratedModel.reply`把批次最后一人设为person_id；`CharacterCoreBase.messages`只对这个人调用recall并填写claims/preferences，其他人只进入participants及原话。当前批次前一位有重要旧边界、后一位插入无关短句时，前者跨窗口边界和关系可能未进入请求。全群主动也用last_person取数，不能据target=all就声称取数覆盖全群。需要有限当前参与者范围、明确标注资料归属、共享总预算和真实来源链；不要给每个人增加一份6条/1800字配额或把全群档案全灌进去。
2. **主动开口与历史连续性。** 当前主动用固定“本机主动时刻”文本做召回/话题匹配，last_person可能来自旧资料导入顺序，重启也未恢复为实际最新发言者。手工保存的小说待续话题可能没有进入这个固定查询。核心取数和活动门槛需要实质共用，主动可沉默且尊重边界；沿用旧时间/次数/开关，不能新开第二个调度器，不能先候选生成再重复润色收费。旧助手正文隔离是诚实的来源限制，不得为连续性编造来源或给用户虚构共同经历。
3. **预览、人物登记与准备事务。** `incoming()`在检查整批大小/空白前先identify，后者立即改people、identities、memory.state以及last_person。预览、新成员非法批次或失败会影响之后正式请求；`prepare_exchange`返回后request_slot已释放，准备结果的有效期还覆盖发送/提交，但普通反馈可在这期间写入使epoch改变。需要一致的暂存/接受生命周期、忙状态和取消处理，避免“反馈让已经按键的轮次提交取消”。审查不能只看成功完成的单一路径。
4. **完整runner的取消窗口。** `PrivateRunner.process_once`读后核查epoch，但busy通知与model.reply之间仍可能暂停；新建Conversation在暂停迭代既有session之后出现时，核心ticket也可能捕获新epoch。需检查观察分支、实例创建、completion调用前与发送前是否共享本轮许可。`validate_pending()`空准备结果当前直接放行，门槛需要分清“没有准备结果”与“允许发送”。不得为了修复取消把可用连续回复退回单次私聊工具。
5. **旧关系与新核心的使用入口。** 原`show_people`仍称“人物关系与记忆”，显示旧SQLite偏好/证据；新核心维护之后它不会同步，于是用户看着旧窗口以为小泽没改。保留显示名绑定和归档访问，但明确哪份实际用于新请求，提供通向同场景核心的入口；不建立第三套关系档案。新MemoryPanel一次构造固定人物下拉框，LiveScene新增成员不代表控件已更新，需要核对开窗期间新增人物和源条目失效的显示。
6. **旧资料兼容的容量与来源。** `_seed_legacy`最多读取128人、每人3个偏好，但长期库总预算256；字面上会出现超过容量的组合。非法旧记录、一次性标记、到期时间未知、迁移中断、同人多别名以及原归档保留范围均要明确。不能为“保留成果”在删除后偷偷从原库取回，不能无声丢弃超量条目或自动清库。这里是待代码审查确认/处理的路径，不是已经动态复现的测试结果。

## 连续接力的本批工作包

顺序可按实际依赖调整，复盘者必须每轮基于上一轮实际修改给出不同的具体任务。任务属于原四类track之一，不需要换控制框架。

- A：收紧完整入口的群/私准备事务、人物暂存与取消窗口。把收件观察、准备生成、允许发送、提交和反馈占用之间的约定写清，保持原非集成模型接口兼容。
- B：群批次当前参与者的分人有效边界、共同话题与取数归属，保证同一请求共享数量/字符/来源预算；正文自称不能改身份，私聊资料不入群。
- C：让原主动开口真正利用允许范围内的近期上下文和有效待续话题；复用当前门槛、停止/临时安静与旧参与配额，统一一条生成路径。决定是否延续话题和实际发送分开；模型可沉默，不用固定指令冒充用户文本。
- D：收拢实际核心与旧归档的界面含义、开窗刷新和资料维护入口；补齐有界旧资料兼容的容量处理与未导入状态。保留API/昵称/原路径、旧数据和旧工具的可达性。更新通俗用法，减少正常聊天里的诊断文案。
- E：前面代码审查完成后，派发**【最终集中验证】**。一次运行有针对性的自动回归、完整旧回归、虚构临时Tk和启动/导入边界检查；如果失败就修复相应问题并验证受影响范围。最后整理用户试用步骤、已实现/代码审查/自动验证/真实体验状态。真实微信和语言效果留给用户最后主动体验，不能用mock冒充。

这是一批有明确缺口的整合工作，不设每包固定轮数或费用/时间上限；不能无限创造“下一阶段”拖住最后验收。A—D完成且审查无具体遗留时自动进入E，不因为用户暂未提供真实聊天样本停在A。遇到实际权限/工具故障照实等待，不自动批准或重复派发未知结果。

## 本批实现纪律

中间轮次不运行基线、单测、全套回归、临时Tk或模型试聊。可以阅读代码/现有测试、写必要回归、做语法与导入静态检查；代码审查通过只写“未运行验证”。用户原话“最后测试”授权E阶段自动做虚构/mock最终验证，不授权实际微信/API。原测试保留，不删断言掩盖退步。不要开发新测试平台，也不把测试数当作人格评分。

项目数据/凭据边界与接力policy保持；不读既有data配置/聊天/人物库或.local-xiaoze，不调用小泽实际API，不自动启用微信、好友/朋友圈/语音功能。开发使用T3已有两个角色：gpt-6-astra复盘、gpt-6.1-sol实现；不改运行时模型。没有真实表达证据不继续堆persona禁令，不用口癖、随机情绪、后处理或第二次润色调用制造“像人”。先改善它获得的上下文与回复对象信息。
