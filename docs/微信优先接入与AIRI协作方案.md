# 微信优先接入与 AIRI 协作方案

日期：2026-11-12。依据本轮用户调整目标与源码/公开文档检查。本文是方案与交接，不表示微信桥接、AIRI新桥接或跨工具调度已实现。

## 优先级调整

用户希望先在微信真实相处，再针对实际问题优化。当前第十二阶段本地实现已交付，不再把更多本地诊断功能作为微信接入前置条件。下一项可执行任务应是“现有微信收发层接入小泽核心”，而不是再扩建一轮本地功能。

本轮只检查、保存方案：未启动微信/监听、未发送消息、未调用真实模型、未删除文件。第十二阶段测试结果沿用原交付记录，没有在本轮重新验证。用户此前报告试聊效果不错，但这不等于当前核心已在微信工作。

## 最短可用路线

保留 `CharacterCore` 的人格、关系、记忆与来源约束，复用旧微信传输。`app.py` 目前通过外部 `wechat-lab/xiaoli/xiaoli_desktop` 源码加载旧私聊/群聊适配；`sessions.MultiRunner` 已有轮流切换会话和共用锁。旧 `ChatModel` / `GroupChatModel` 与新核心尚未统一，不能仅把窗口上的阿澄改名就视为升级。

建议按以下顺序交付可使用的结果：

1. 先接主人单一私聊：现有收件与目标核对 → 小泽生成 → 现有发送层 → 返回发送状态。保留人工暂停和目标白名单。入口清楚标出当前账号、目标、预览/真实回复状态，避免误开旧配置。
2. 用虚构数据验证目标错配、自回声、重复收件、生成中暂停、发送失败/不确定几个关键路径；再由用户开启一次私聊实际试用。不要为进入试用再要求完成多阶段本地体验。
3. 私聊可用后加目标群，再接私聊与群聊轮询。沿用场景/人物隔离；OCR显示名匹配不能升级为账号认证，无法确定时不凭昵称猜主人。
4. 基于实际使用问题修复漏收、错发、重复、延迟，再接微信中的有限主动表达。现有“自动本地采用”不能直接变成微信自动发送。

关键接口不能省略：新 `exchange` 成功会提交本地对话，并不证明微信发送成功。生成与发送之间需要最小状态合同，区分已生成、尝试发送、可确认成功、失败/结果不确定；只记界面/适配层确实能证明的结果，不把点击成功写成对方已收到或已读。发送不确定时停止并提示，不能再次调用模型或自动重发制造重复。具体如何复用提交事务，以实现时源码为准；不另建一套人格/记忆。

真实运行需用户明确启动和限定目标；不把阅读本文当成现在就允许监听/发送。后续若明确授权微信桥接开发，可直接完成常规本地实现和mock验证，不再以早期“微信最后”拒绝推进；真正上线范围仍应清楚。

## AIRI：有帮助，但不挡住微信使用

已核查 [AIRI仓库](https://github.com/moeru-ai/airi)、仓库LICENSE（MIT）、README、[server-sdk说明](https://github.com/moeru-ai/airi/tree/main/packages/server-sdk)与[WeChat文档](https://github.com/moeru-ai/airi/blob/main/docs/wechat.md)。检查时仓库未归档，公开元数据显示当日有推送；这不能证明每个接口稳定。README支持Live2D/VRM、语音等方向，记忆仍标为进行中；所谓WeChat链接实际是项目交流群说明，不是现成微信机器人适配。

本机旧 `airi-setup` 已有本地WebSocket伴随脚本，使用 `context:update` 和 `input:text`；后者会触发AIRI自身生成。旧脚本还有自己的主动计时和记忆工具。不要与小泽自动开口直接并行运行，否则可能出现两次生成、两套记忆和重复开口。旧说明不证明当前安装版本已配置语音。

推荐一个核心：小泽负责人格、关系、记忆和是否开口；微信负责收发；AIRI以后负责形象与语音。AIRI故障不应阻止文字聊天。公开SDK已核实有连接/事件/发送能力，但“外部生成文本直接呈现和播报、完全绕过AIRI自身生成”的准确接口仍需按本机版本核对，不能现在声称已经打通。先不迁移整套核心进AIRI，也不以AIRI安装/改造作为微信接入门槛。

## T3 与持续开发自动化

本机 `C:\Users\ZhuanZ\.t3\bin\t3.cmd` 的实际帮助包含 `thread start/send/show/list`。本轮只执行帮助，没有新建任务、读取任务正文或发送指令。`thread send <thread> <message>` 支持 `--wait --json`，消息为 `-` 时从标准输入读取；帮助注明退出码1表示运行失败、2表示等待用户回答。具体服务连接和模型可用性尚未做一次真实派发验证。

因此可以通过CLI交接和等待，Computer Use作为界面备用，不必每次靠点击窗口。可实现“完成当前明确任务 → 写HANDOFF/验证结果 → 向指定T3任务发下一项明确工作 → 等待并检查”的有界流程。用户尚未指定本轮要派发的任务，故没有执行派发。

它不等于无限自动完成需求。需要一个实际控制流程负责队列、任务ID与防重复、单一源码写入者、时间/费用/轮数上限、失败及需要回答时停止。聊天里说‘完成后继续’不会自动创建这些机制。开发自动化与小泽微信运行是两件事，不能把跨软件点击当成微信机器人传输。

当前Codex/T3的单写入者只是人工约定，尚无跨工具进程锁。交接以磁盘HANDOFF与实际结果为准，不假定聊天历史同步。电脑休眠、断网、权限提示、模型额度都会打断；Computer Use和桌面微信尤其依赖电脑运行及可操作的桌面。云端开发任务不会让关闭的本机微信继续在线。
