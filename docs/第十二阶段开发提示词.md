## 三、同一套判定的只读状态

先用可控时钟与虚构话题复现当前状态说明的局限，写小设计，再实现一个最小结构化状态投影。优先复用实际策略和核心门槛，由相同判定产生调度结果与展示理由，避免另写一套“看起来像”的规则。具体接口名由实际代码决定，不硬套框架。

状态至少能忠实区分：关闭、错误后停止、等待空闲、输入/子窗/最小化/暂停暂缓、安静时段、缺少已启用/已确认/已到时间的话题、待处理草稿、成功评估后的冷却、等待用户回应、滚动小时上限、程序会话上限、正在评估。不要将所有本地阻止叫成模型沉默。

显示的建议组织为“当前状态 + 具体等待条件 + 可采取的一步操作”，让普通用户看懂。例如“距满足空闲条件还约4分30秒；有有效话题时才可能评估”“已有一条草稿，先查看或处理”“本次自动请求已达到会话上限”。不能把倒计时写成保证到点就说话，也不引导反复重启绕过会话配额。

需要数量时分清自动请求尝试、自动本地开口、手动调用；来源取自已有预算，不用模型token或用户消费金额作推断。模型选择silent只有原事务明确返回时才能这样描述。本地门槛无请求，不给它算模型费用或新冷却。

**只读约束：**展示不能调用`due()`、`activity()`等会更新last_check/last_activity/note/活动版本的函数来“顺便获取状态”，不能触发候选生成、提取、采用或新的请求。不能修改文件、完整记忆、epoch、paused、inflight、last_trace/last_notice、自动运行代次、计数、开关、冷却或证据缓存。现有snapshot的到期投影与只读预检可按原约束复用；不得把预览中的过期投影写回正式库。

尽可能提炼一个共享的纯判定部分，再由现有调度入口承担更新last_check等动作；不能为了漂亮的状态页面改变真正调度时机、优先级或取消条件。状态明确是“当前检查结果”，不是历史实际请求清单。多条件并存时显示首要阻止原因或少量并列条件，说明判断顺序；不能因状态显示顺序与原执行路径不同而声称调用发生。

## 四、时间、刷新与执行事实

剩余空闲/滚动窗口使用注入单调时钟，安静时段用现有北京时间。冷却根据实际last_check与当前时钟，小时上限根据实际尝试时间戳，不能与成功次数混用。剩余时长下限为0；达到阈值后仍要等真正的定时检查及其他门槛。会话上限没有“过一小时恢复”的倒计时。

显示与调度解耦：状态倒计时可以适度刷新，但不增加每秒核心快照/磁盘访问/记忆遍历，避免100ms poll反复昂贵计算。仅当原数据/选择改变或合理的时间边界到达才重新取数，纯时间显示用现有时钟。若使用临时派生缓存，只含状态码/必要时刻/数量，定义失效与有界生命周期，不复制正文/配置或延长被删资料寿命；不为本功能默认增加长期缓存。没有实测就不宣称性能提升。

本阶段默认只改善当前状态，**不新增自动运行历史档案**。已有完成结果可在原提示区域保留实际结果；不要从今天状态重算“上一次为什么沉默”，也不把“待处理草稿”推断成刚刚调用了模型。确需区分最近完成事实，最多在当前自动会话保留一个无正文、无配置、无动态来源标签的短期结果，并在小设计中说明必要性、范围与清理；不写盘、不复制完整请求。

原busy、请求槽、Core→策略→预算锁顺序、run/代次、commit ticket、draft_id及采用收据保持。查看状态不能挤占请求槽、取消正常在途生成，不能使迟到请求重新获得资格。停止/切范围/配置/输入/维护/删除/到期仍按原规则处理；状态异常应沿用已有停止或降级机制，不自动重试模型，也不把已提交结果显示成未提交。

实际语句不自然时沿用回复旁反馈入口。采用事件没有普通exchange同等级瞬时直接取数清单，仍诚实降级；不要给用户一种“状态页知道模型为何这么想”的错觉。

## 六、少量真实体验与条件式优化

没有样本也可完成状态入口与离线验证后交付，不无限等用户，也不自动调用模型补样本。给用户一个可选体验过程：白天在主人私聊准备一个真实想继续的、由用户确认的话题，开启两个开关，正常使用一段时间；观察一次自然开口或一次有解释的等待，接一句话，再明确结束。模型调用由用户开启后的原功能进行，开发者不代开、不另加调用。

用户愿意反馈时，最少报告“什么时候期待开口、实际状态、是否打扰、哪句不自然”即可；只要分析语言才需要用户明确授权的少量相关文本，不要求整库或Key。用户已验收旧阶段，不再要求全量重复测试。

区分等待条件未满足、界面说明不清、请求/提交失败、资料没取到和表达不自然。只对本阶段可复现的问题局部修复；没有证据不改默认频率/夜间/配额/人格，不把正常沉默当故障，也不强制每次出草稿。
