# 微信收发路线纠偏与串发复盘

日期：2026-11-15。依据用户报告“群里提问却私聊收到，只有一轮，不能动鼠标，必须前台”、所附诊断截图与当前代码。没有查看实际聊天内容、配置、Key或正式人物库，没有打开微信、监听、真实发送或真实模型请求。

## 结论

当前前台视觉收发层不符合用户“正常使用电脑时，群聊和私聊持续后台自动回复”的目标。先前不断修OCR与模拟回归，只能改善这个兼容层局部可靠性，不能满足后台要求；未充分揭示路线限制，也没有以真实收发体验作为最终验收，方向需要纠正。人格、关系、选择性记忆、对话与主动表达核心仍可复用，不应重建。

本轮先补已发现的实际串发机制，随后停止把增加OCR兼容视为实现后台运行。更换模型或加入AIRI形象/语音不能解决传输层问题。本文是复盘和替换方案，后台接入尚未实现。

## 截图实际证明与不能证明的事

截图是live、enabled、ready，群聊visible_messages=8、received_messages=1、state=sent，私聊received_messages=0且会话列表定位错误。群消息读取已较之前前进，但sent只表示底层按键调用返回，不能证明发进正确群或送达。私聊0条也不符合“私聊先收到消息再正常生成”的解释。此截图不能独立证明串发原因或首次之后不回复的全部原因；需要区分识别不到新消息、游标unchanged、列表定位和发送焦点。当前并非preview一轮后自动暂停，也没有证据归咎模型或群名。

## 发现并复现的串发缺口

app.py使用current_chat_backend包装原VisualBackend；sessions.RoutedTransport在共享RLock下切换目标，core.ScopedTransport先核对主窗口标题再调用send_text。

但原VisualBackend.send_text(chat,text)的chat参数未用于选择或确认目标；它按主窗口坐标点击、向全局剪贴板写文字、全局Ctrl+V和Enter。原_foreground在调用SetForegroundWindow后直接返回True，既不检查Windows是否拒绝切前台，也不检查粘贴/回车前的实际前台窗口。锁只约束程序内部，不约束用户或独立私聊窗口。主窗标题正确不代表全局按键进了该主窗。

test_desktop_sender.py用AST隔离执行**原send_text函数**、mock键鼠/剪贴板，复现“主窗群标题正确，前台为另一个私聊窗口，发送目标参数为群，原函数仍将Enter发到私聊”。这是已复现的故障机制，吻合用户报告；没有扫描真实记录证明当天某一条的逐步时序，故不声称已还原那次唯一根因。

## 已做的止损修复

- 新desktop_sender.py复用现有输入框几何；在前置后、点击前后、粘贴前、回车前，检查真实前台HWND、精确目标名/会话类型和有效发送许可；慢OCR后再次检查焦点/许可。
- current_chat_backend仅为具有原生桌面输入几何的后端装配此受检发送方法；Fake/事件后端仍使用原有明确目的地发送合同。没有改上游安装源码或全局Monkey Patch。
- ScopedTransport把当前can_send传到受检发送方法；暂停后不继续粘贴/回车。底层异常继续按发送结果不确定处理，不自动重试；外部操作开始后不承诺撤回。
- 旧单主人诊断桥VisualTransport也传递当前can_send，保留原有“按键不等于送达、结果不确定即停止”的合同，不改变完整版连续会话策略。
- 界面明确当前是占鼠标、键盘、剪贴板的前台视觉兼容模式，不再让“自动回复”暗示真正后台通道。

**能力边界：**最后一次检查与真实按键之间仍有竞争窗口，共享用户桌面不能做到原子收发。保护减少已复现的风险，不证明零错发，不解决后台运行。粘贴后取消可能留下未发送草稿/剪贴板内容，不自动清空其他窗口或恢复剪贴板，避免破坏用户后续输入。该版本暂不应作为无人值守可靠收发验收通过。

## 后台路线与下一项工作

需要基于消息事件和稳定会话ID的收发适配：消息携带chat_id、sender_id、is_group、message_id；同一事件的回复固定发回其chat_id，身份不从当前窗口推断。核心仍使用现有小泽场景/人物与prepare/commit、取消/不确定结果合同；稳定ID来源未验证前不擅自把显示名迁成账号身份。

1. 优先验证一个当前账号实际可用的个人微信消息接入方案：明确支持客户端版本/登录方式、能否加入当前普通微信群、费用和许可证；在隔离环境用机器人独立账号完成最小收发。先验证适配器，再接人格，不重建本项目。
2. 适配器验收必须先过：用户移动鼠标/使用其他程序不干扰；群和私聊新事件都有稳定会话归属；交错连续消息不串发不漏回；断线/失败不盲目重发。先用虚构/mock检查合同，再由用户明确触发少量实际消息。不要用单测数替代这些实际体验。
3. 若当前没有可验证的个人微信后台适配器，可把现有视觉模式放到单独虚拟机/备用电脑，释放用户主机鼠标；机器人所在桌面内部仍依赖窗口前台，仍需验证路由，因此只是过渡，不能改名宣称API后台。
4. 不自动降级微信、不安装Hook/DLL、不登录第三方协议服务、不迁移正式库。当前旧通道保留作兼容/诊断；主机后台路线验证通过再接同一小泽核心。云服务器仅提供运行机器，不能自动把桌面脚本改成消息接口。

企业微信机器人/公众号官方接入与现有普通个人微信群不是同一场景，不能拿前者冒充后者已解决。AIRI、AstrBot、Wechaty等框架与微信实际接入提供方也要分清；安装框架本身不证明目标账号可登录并后台收发。
