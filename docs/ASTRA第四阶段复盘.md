# ASTRA第四阶段复盘与优化

日期：2026-11-11。本次检查第四阶段实际代码，补充复现并完成局部修复；没有开始第五阶段实现，也没有启动微信、后台调度或真实API调用。

## 结论

第四阶段的方向正确：普通生成内容有可追溯来源，本地草稿可以明确成为一条真实的本地助手消息，再接住用户回复。多跳删除、场景隔离、重复采用和原子提交已有行为验证。但初次交付仍有更正资料误失效、群内临时状态过滤不一致、话题重新开启恢复旧内容、显示异常中断后续回调的问题，不能只凭161项通过就认为基础体验没有阻断点。

这些已在本次修复。建议进入一个范围较小的第五阶段——**真实多轮体验与针对性质量优化**。当前最缺的是实际模型对话证据，不宜立即叠加微信、定时主动说话、复杂情绪或向量记忆。第五阶段应先体验，再依据具体失败决定改什么；不要把下一阶段等同于必须再写一大套架构。

## 本次发现、复现和处理

| 发现 | 复现场景 | 修复与边界 |
|---|---|---|
| 手动更正后生成被取消 | “我喜欢简短回复”改为“回答可以详细展开”；下一次真实exchange路径完成模拟生成，却以资料失效拒绝保存；从更正记录建立话题也会失效 | 来源记录区分“实际读到的用户原话”和“有效维护记忆”，仍保留全部根ID用于关联删除。旧原话失效不再使有效更正资料也失效 |
| 群内另一人的临时例外误取消回复 | 小林长期不喝咖啡、今天喝咖啡；小乔聊小说，组装请求仍带小林旧原话，提交校验却认为来源无效 | 普通取数、助手有效性和话题检查共用全场景来源过滤，按各人槽位判断临时覆盖，避免请求前后条件不一致 |
| 同一时间暂停再开启话题，旧回复重新出现 | 可控时钟下pause→activate，内容和时间摘要恢复原值，旧助手历史再次可用 | 每次明确修改、停止、拒绝或重新开启生成新revision_id；摘要包含它，重新开启不恢复旧版本正文 |
| 回复已经保存，显示异常却中断后续回调 | 消费完成事件后render抛错，旧poll不再安排下一次回调，控件也可能保持忙状态 | 明确报告保存结果与显示失败，恢复控件并在finally继续安排事件处理，不重新请求模型或重复提交 |

另补齐删除话题对关联助手正文、未知来源旧正文和反馈的影响提示；只读v2的复制操作在触碰剪贴板前先拒绝写入。验证了跨话题派生候选在删除其间接来源后清空正文和反馈，该路径原来已有效，保留为回归而不冒称新增修复。

主人仍唯一为孤月大人，固定温柔、尊重、善意理解和含蓄亲近原则未改。这里没有用更多绝对化提示来掩盖工程问题；真实表达是否自然仍需体验。温柔允许诚实分歧，也包括尊重“不想聊”的边界。

## 来源语义和兼容调整

内部文件仍为v3、路径仍为 `*-v2.json`。新生成的 `reply_trace` 升为version=2，增加 `raw_source_ids`，是全部 `source_ids` 的子集：前者表示模型实际读过的原话，后者还含有效记忆/话题的删除祖先。旧原话更正/到期时，停止使用依赖该原话的内容；维护后的有效记忆按其record_id状态判断。明确关联删除仍按全部根来源清理，不因更正而切断删除链。

旧trace v1继续加载并沿用保守语义：把其全部根来源视为可能读过的原话，绝不猜测过去到底输入了什么。仅打开不重写；后续新生成才产生v2来源。没有来源的更旧助手记录仍隔离。本次没有读取或迁移用户实际文件；不建议旧程序降级写入，因为旧代码不认识新来源子版本。原有v2顶层文件仍须通过已有按钮明确升级为v3。

旧话题没有revision_id仍可读取，第一次修改时增加；原摘要无此字段的计算保持兼容，不仅因打开文件而让所有旧助手历史失效。候选策略升为 `local-candidates-4`，旧非公开待处理草稿按策略不匹配失效，需重新评估。公开素材仍独立，不扩大取数范围。

容量保持128根/32记忆/16话题依赖及12条近期容器。来源集合有界，超预算在请求前省略相应助手内容或拒绝；没有借此次修复增大上限或引入服务。请求级保守依赖仍可能多撤销一些并未实际复述旧资料的助手文字，这个取舍尚待真实体验。

## 验证证据

新增 `test_stage4_review.py`：最初4项中3项实际失败，分别为两个错误取消和话题重开恢复；跨话题删除已有保证通过。随后加入显示回调失败用例，旧实现会抛错中断；加入旧trace v1只读加载及保守传递验证。最终6项新回归与既有测试合计输出 `Ran 167 tests in 2.638s`、`OK`。

`smoke_local_ui.py`通过既有多轮、记忆、候选和输入保留流程。`smoke_dialogue_ui.py`通过选择证据、确认话题、采用、接话、反馈、删除、显示恢复和v2显式升级。后者在沙箱内仍遇Tcl初始化环境错误，经工具审批在沙箱外运行同一临时虚构脚本通过。正式CMD `--check`通过。没有真实模型调用或实际剪贴板改写。

通过的证据是请求内容、临时文件、重启、取消和Tk回调，不是“像真人”的结论。真实模型的口吻、好奇、温柔、主动分寸和长时间运行仍未验证。

## 是否需要下一阶段

**需要，但建议改变推进重心。** 四个阶段已形成可用的本地人物试验底座，继续仅用合成回复增加功能，很难知道小泽是在变得自然还是只是控件更多。先用现有入口取得三类真实模型体验，再把有证据的问题排到开发前面。

1. **主人连续聊天：** 同一件小事聊6—10轮，中间有分享、不同意见、疲惫和换题。看她是否接具体内容、温柔但不过度迎合，有没有机械安慰/反问。
2. **开口与接话：** 标记一条小说/音乐话题，评估并采用，再接两三轮；明确说想安静。看候选是否有新内容、是否重复问过的问题、是否尊重停止。
3. **朋友/群聊与记忆修正：** 虚构朋友各有边界，主人参与，再更正一条偏好。看身份、态度和信息范围是否清楚，改正后能否自然继续。

一次记录一个具体问题即可：场景、前后必要几句、期望怎样、当前模型与规则版本。不要提交Key，不用整段真实微信群记录，也不自动上传。没有必要先增加大规模评分、每轮抽取或后台自动评测。

第五阶段优先级建议：先修实际体验中频繁出现的阻断/误记/串人，再改善重复追问、主题硬转和操作负担。若用户经常要求暂时安静却很快又被打扰，再实现有明确解除方式的持久免打扰；若“这个话题不聊了”经常关闭太多话题，再做选定话题的范围控制。避免在没有样本时同时扩展这两套状态。

微信执行、后台调度和自动发布仍留到人物核心和本地体验稳定以后。即使下一阶段自然程度变好，外部执行仍需独立的身份、范围、回执和失败设计，不能因为本地采用成功就直接打开真实发送。

## 下一阶段前的体验判据

不规定“必须达到多少测试或多少分”。更有用的判断是：更正与删除不会阻断后续正常交流；主人/朋友不串身份；主动开口后能接话；想安静时能停止；用户能指出具体哪里自然、哪里生硬；当前失败不会引起外部动作。前五项中的语言体验部分尚需真实模型样本。

本次已完成第四阶段复盘修订。没有实现第五阶段或自动调用真实API，后续应根据上述体验结果确定第五阶段任务的最终范围。
