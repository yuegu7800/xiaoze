## 复盘结论

第十阶段的正常生成、互斥、配额和采用路径在本轮262项修改前基线中通过，但若Tk读取/绘制、定时器或工作线程启动失败，部分清理路径不完整。本轮复现并修复6类问题：

| 触发 | 修复前结果 | 本轮处理 |
|---|---|---|
| 自动工作线程启动抛RuntimeError | 自动关闭但busy仍为True，普通发送持续禁用，活动run残留 | 线程未启动时结束run、释放busy、停止定时器并恢复控件；不计请求、不重试 |
| 草稿提交后的完成回调读取环境抛TclError | 队列事件已消耗，active仍残留，后续一直认为有自动运行 | 环境核对纳入完成处理的异常边界，结束该run并停止自动；已提交草稿保留，不采用 |
| 定时检查更新状态栏抛TclError | 执行中断，自动仍显示开启，但没有后续定时回调 | 绘制与排程放在同一异常边界内，失败明确停止；清理不依赖状态栏 |
| 关闭窗口时自动状态栏绘制失败 | close在暂停Core/销毁窗口前中断 | 关闭路径不绘制自动控件，先取消自动，再按原流程暂停Core/清回调/销毁 |
| 首次注册after回调抛TclError | 开启流程抛错，策略仍为enabled且无定时器 | 启动边界捕获Tcl错误，关闭自动与开关，不留无调度的开启状态 |
| 只读预检通过后，话题在实际评估前到期 | 没有调用模型/提交冷却，但显示“保持沉默，等待10分钟冷却” | 使用原候选事务给出的实际reason，区分本地阻止与模型合法silent |

首批4条实际Tk用例修复前得到2个失败、2个错误，分别直接触发上述前4项；没有把测试导入失败或缺少新函数当成产品失败。后续定时器注册用例在修复前直接抛TclError，时钟驱动的本地阻止单测在修复前理由断言失败。另增加“双状态栏同时不可绘制，停止仍生效”的实际控件覆盖。

## 修改与提交边界

源码仅修改`local_chat.py`与`auto_opening.py`。

- `stop_auto`先取消策略与回调，再尝试更新界面；自动状态栏和普通提示栏同时不可绘制时，取消仍完成。关窗使用不绘制的停止路径。未改变HTTP不能撤回的语义。
- `start_auto_request`只在工作线程成功启动后把任务交给线程；启动/控件准备失败时清理本轮状态，不伪造模型请求、成功生成或本地提交。普通手动聊天仍可继续，测试实际发送一轮mock回复验证恢复。
- `auto_tick`把预检、状态绘制和后续排程纳入异常处理；`toggle_auto`也覆盖首次排程/绘制失败。不会自动重开或补偿请求。
- `finish_auto_request`把环境读取与采用放进同一异常边界。已结束的工作线程不再留下无人处理的active。已有草稿沿用原来源、期限和待处理状态；重复完成回调不恢复旧资格、不自动采用。
- `AutoOpening.finish`显示原事务reason。只有实际模型合法silent才有原事务确认的10分钟冷却；本地到期挡住时不再冒称模型运行或新增冷却。

原request_slot、Core锁、epoch/commit ticket、具体draft_id、输入保留、取消代次、来源删除和采用收据均沿用。没有改候选JSON协议、模型参数、API保存配置、persona、身份规则、召回容量或持久格式。没有新增依赖、调度存档或全文日志。
